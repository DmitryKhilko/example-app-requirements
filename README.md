# example-app-requirements
Пример организации требований с использованием подхода "Documentation as Code"

Адрес сайта задан параметром `site_url` в `zensical.toml`.

## Как устроена карта фичей

Карта фичей (`docs/feature-map.md`) — иерархическое оглавление «Модуль → Субмодуль → Фича» со ссылками на
спецификации. **Вручную её не редактируют**: её формирует скрипт `scripts/generate_docs.py` по метаданным
(YAML Front Matter) в начале каждой спецификации.

```
Слияние в main ──► feature-map: python scripts/generate_docs.py ──► коммит docs/feature-map.md (если изменился)
                                                                        │
                                                                        ▼
                                                  deploy: zensical build ──► Pages
```

Workflow: `.github/workflows/deploy.yml` (GitHub) или `.gitea/workflows/pages.yaml` (Gitea). Карта обновляется
только при слиянии в `main`; в рабочих ветках `docs/feature-map.md` не трогают, поэтому конфликтов слияния в нём не
возникает.

### Метаданные спецификации

Шаблон — `templates/feature-spec-template.md` (как с ним работать — в разделе «Шаблон спецификации» ниже). Метаданные —
блок YAML в самом начале файла между строками `---`.

| Поле           | Обязательное | Описание                                                                                          |
|----------------|--------------|---------------------------------------------------------------------------------------------------|
| `id`           | да           | Код спецификации: латиница и цифры, группы через дефис (например, `SHOP-CAT-SF-005`). Уникален среди всех спецификаций, включая архив |
| `module`       | да           | Модуль (верхний уровень карты)                                                                    |
| `submodule`    | нет          | Субмодуль; по умолчанию `Общее`                                                                   |
| `feature_name` | да           | Название фичи — текст ссылки в карте                                                              |
| `status`       | да           | Статус фичи по жизненному циклу, см. таблицу ниже; неизвестное значение — ошибка                 |
| `order`        | нет          | Порядок в левом меню (целое число, меньше — выше), см. «Порядок разделов и спецификаций»          |
| `doc_version`  | нет          | Версия документа строкой в кавычках, например `"0.01"`                                            |
| `owner`        | нет          | Ответственный: «Фамилия Имя»                                                                      |
| `task_id`      | нет          | Номер задачи в трекере строкой (например, `"1"`); в «паспорте» выводится ссылкой, адрес задаётся в `zensical.toml`, `[project.extra.tracker]` → `task_url` |
| `relise_id`    | нет          | Номер релиза, в который вошла спецификация: числа через точку, строкой в кавычках (например, `"1.2.1"`); по нему строится страница «Релизы» |
| `relise_date`  | нет          | Дата релиза в формате ДД.ММ.ГГГГ строкой в кавычках (например, `"15.09.2026"`); у спецификаций одного релиза одинакова. Выводится в заголовке блока релиза и в «паспорте» |
| `template`     | да           | Шаблон страницы: всегда `"spec.html"`; выводит над заголовком «паспорт» из метаданных, см. «Паспорт спецификации на сайте» |
| `relations`    | да           | Блок связей с другими фичами; поле `relations.depends_on` в нём тоже обязательно (если зависимостей нет, `depends_on: []`) |
| `icon`         | —            | Значок статуса; вручную не заполняют, поле ведёт скрипт                                           |

**Обязательность берётся из шаблона.** Скрипт читает комментарии в `templates/feature-spec-template.md`: поле обязательно,
если в комментарии к нему написано «обязательное» (у вложенных полей так же, например `relations.depends_on`); поля с пометкой
«необязательное» и без пометки заполнять не обязательно. Изменили комментарий в шаблоне — изменились и проверки, править
скрипт не нужно. Для списков и наборов (`relations`, `depends_on`) «обязательное» означает, что поле есть: пустой список
`[]` допустим. Для остальных полей значение должно быть непустым.

Каждая ссылка карты ведёт на раздел «Описание» спецификации и показывает его в окне предпросмотра при наведении
(`{data-preview}`).

Статьи без полей `module`, `submodule`, `feature_name` (например, глоссарий) в карту не попадают. Поэтому любой `.md`-файл в
папках `docs/specifications/` и `docs/archive/` (кроме сформированных `index.md`) обязан иметь метаданные спецификации,
иначе проверка сообщает об ошибке: такой файл молча выпал бы из карты.

#### Статусы фичи

| Статус        | Значок                   | Что означает                                                                      |
|---------------|--------------------------|-----------------------------------------------------------------------------------|
| `backlog`     | `:lucide-file:`          | Зафиксированное сырое требование или идея                                         |
| `analysis`    | `:lucide-file-pen-line:` | Детализация и согласование требования                                             |
| `ready`       | `:lucide-file-check:`    | Утверждённое требование, готовое к реализации                                     |
| `development` | `:lucide-file-braces:`   | Требование в работе у команды разработки и тестирования                           |
| `released`    | `:lucide-file-text:`     | Код, связанный с требованием, успешно развёрнут на проде                          |
| `archived`    | `:lucide-file-archive:`  | Отклонённое или устаревшее требование; ставится автоматически для `docs/archive/` |

Допустимы русские синонимы: `бэклог`, `анализ`, `готово к разработке`, `разработка`, `реализовано`, `архив`.
Подписи статусов также заданы в `[project.extra.status]` файла `zensical.toml`; при изменении набора статусов
правьте оба места (`STATUS_ICONS`/`STATUS_TITLES` в скрипте и `zensical.toml`).

### Шаблон спецификации и проверки

**Как создать спецификацию.**

1. Скопируйте `templates/feature-spec-template.md` в `docs/specifications/<папка-модуля>/<имя-файла>.md`. Имя файла —
   латиница, цифры и дефис, без пробелов. Оно же служит идентификатором фичи в блоках `relations` других спецификаций.
2. Заполните метаданные и замените все значения-подсказки («Название модуля», «Название фичи», «Фамилия Имя»,
   `Буквенно-цифровой код спецификации`).
3. В заголовке первого уровня замените `feature-slug` на имя файла без расширения: `# Отмена заказа {#order-cancel}`.
4. Заполните разделы. Комментарий с правилами в конце шаблона можно удалить, на проверку он не влияет.

**Обязательные заголовки.** Все заголовки шаблона обязательны: с тем же названием, уровнем и якорем. Дополнительные разделы
добавлять можно, но тоже с явным якорем.

| Заголовок              | Якорь                  | Что в разделе                                                          |
|------------------------|------------------------|------------------------------------------------------------------------|
| `# Название фичи`      | `{#имя-файла}`         | Заголовок первого уровня, он один; якорь совпадает с именем файла      |
| `## Описание`          | `{#article-overview}`  | Что делает фича и зачем нужна; на этот раздел ведёт карта фичей        |
| `## Основной сценарий` | `{#main-scenario}`     | Шаги основного сценария                                                |
| `## Критерии приёмки`  | `{#acceptance-criteria}` | Проверяемые условия                                                  |
| `## Критерии релиза`   | `{#release-criteria}`  | Внешние, бизнес- или технические условия включения фичи на проде       |

Раздел «Взаимосвязи» (`{#relations}`) в шаблон не входит: его создаёт скрипт сразу после «Описания». Добавлять его в текст
вручную нельзя (повторный заголовок с таким якорем — ошибка).

**Что проверяется.** Проверка охватывает **все** спецификации, включая архивные и созданные раньше, и показывает все
замечания сразу (с файлом и строкой).

Ошибки (коммит или сборка останавливаются, код возврата 1):

* не заполнено обязательное поле метаданных; не заменено значение-подсказка в `module` или `feature_name`;
* `status` с неизвестным значением; `order` не целое число; неверный формат блока `relations`;
* `id` не соответствует формату или уже используется другой спецификацией;
* у заголовка нет явного якоря; якорь недопустим (кроме латиницы, цифр, `-` и `_`, должен начинаться с буквы) или повторяется
  в файле;
* заголовка первого уровня нет или их несколько; его якорь не совпадает с именем файла;
* нет обязательного раздела из шаблона или он называется иначе, чем в шаблоне;
* `.md`-файл в `specifications/` или `archive/` без метаданных спецификации;
* ошибки связей (см. «Взаимосвязи фичей») и отсутствие маркеров меню в `zensical.toml`.

Предупреждения (не останавливают):

* поле метаданных, которого нет в шаблоне (чаще всего опечатка);
* не заменено значение-подсказка в необязательном поле (`submodule`, `owner`);
* разделы идут не в порядке шаблона;
* вручную созданный `index.md`, повтор `order` в одной папке и другие замечания, описанные ниже;
* шаблон не найден: тогда проверяются только `module`, `feature_name` и раздел «Описание».

### Паспорт спецификации на сайте

Zensical не выводит метаданные (YAML Front Matter) на страницу. Поэтому каждая спецификация подключает шаблон страницы
`theme-custom/spec.html` полем `template: "spec.html"`. Шаблон выводит над заголовком «паспорт»: код (`id`), статус,
модуль, субмодуль, ответственный (`owner`), версия документа (`doc_version`), задача (`task_id`), релиз (`relise_id`), дата релиза (`relise_date`) и, если поле задано, спринты (`sprints`).
Ключи `task_id`, `relise_id` и `relise_date` выводятся всегда, даже если значение пусто; номер из `task_id` показывается ссылкой на задачу (`task_url` + номер).

* **Не выводятся:** `relations` (связи показывает раздел «Взаимосвязи», который формирует скрипт), `feature_name`
  (это заголовок страницы), `order` и `icon` (служебные поля меню).
* **Подписи статусов** шаблон берёт из `[project.extra.status]` в `zensical.toml`; если подписи нет, выводится код статуса.
  Спецификация из папки `archive/` показывается со статусом «Архив», даже если в метаданных остался прежний.
* **Стили** паспорта — `theme-custom/stylesheets/extra.css`, раздел 12.
* **Новое поле в паспорте:** добавьте блок `{% if meta.<поле> %}…{% endif %}` в `theme-custom/spec.html`.
* Поле `template` обязательно (его проверяет скрипт по шаблону спецификации), значение менять не нужно.
* Шаблонизатор Zensical — MiniJinja: произвольные функции Python в шаблонах недоступны.
* Имя файла шаблона не должно совпадать с файлами темы (`main.html`, `base.html`).

### Страница «Релизы»

Страница `docs/releases.md` формируется скриптом так же, как карта функциональностей (вручную её не редактируют; в меню
она стоит после карты). В неё попадают спецификации, у которых заполнен `relise_id`.

* **Блоки релизов.** На каждый релиз — сворачиваемый блок с номером и датой релиза («Релиз 1.2.1 (15.09.2026)»; дата — поле
  `relise_date`, без неё скобки не выводятся) и числом спецификаций (те же блоки, что у
  модулей на карте). Релизы идут от новых к старым (`1.10.0` новее `1.9.0`). Раскрытие работает как у модулей: открытым
  остаётся один блок.
* **Панель релиза.** Список вошедших спецификаций: название (ссылка на спецификацию) и под ним текст раздела «Описание».
  Окно предпросмотра у этих ссылок отключено: страница `releases.md` исключена в `sources.exclude` настройки предпросмотра
  в `zensical.toml` (иначе расширение добавляет предпросмотр всем ссылкам на `*.md`). Спецификации идут по модулям (порядок `nav-order.yml`), затем по полю `order`.
* **Скачивание.** Кнопка «Скачать в текстовый файл» в панели сохраняет список релиза в файл `release-<номер>.txt`
  (UTF-8, строки Windows): номер и дата релиза, число спецификаций, затем название, код и описание каждой. Файл собирается в
  браузере из самой панели, поэтому всегда совпадает с тем, что видно на странице. Скрипт — `theme-custom/javascripts/releases.js`.
* **Плитка** «Релизы» на странице «О программном продукте» — в `docs/index.md` (файл ведут вручную).
* **Меню.** Порядок вкладок и их названия задают `ROOT_PAGES` и `TRAILING_PAGES` в `scripts/docgen/config.py`: «О продукте»
  (на самой странице заголовок «О программном продукте»), «Глоссарий», «Карта функциональностей», «Спецификации»,
  «Архив спецификаций», «Релизы» (последняя вкладка).
* **Проверка.** Неверный номер (не «числа через точку») или дата (не ДД.ММ.ГГГГ) — ошибка; у спецификаций одного релиза разные
  даты — предупреждение (на странице берётся самая частая). Если ни у одной спецификации нет `relise_id`, страница
  показывает сообщение «Релизов пока нет».

### Взаимосвязи фичей

Связи фичи с другими фичами задаются в метаданных блоком `relations`. На сайте в каждой спецификации сразу после
раздела «Описание» выводится раздел «Взаимосвязи» (`{#relations}`): **схема Mermaid и таблица только для этой
фичи и её прямых соседей**. Полная карта связей всего продукта не строится.

```yaml
relations:
  depends_on:                       # без этих фич данная не работает
    - feature: payment-sbp
      note: "Возврат средств выполняется тем же способом, которым оплачен заказ"
  extends: [filter-categories]      # добавляет возможности уже работающей фиче
  replaces: [search-old]            # заменяет (обычно архивную) фичу
  related: [auth-sms]               # просто связана
```

| Тип связи    | Когда использовать                                              | Стрелка на схеме | Строка в таблице (прямая / обратная)                  |
|--------------|-----------------------------------------------------------------|------------------|--------------------------------------------------------|
| `depends_on` | Без другой фичи эта не работает                                 | сплошная         | «Зависит от» / «Используется в»                        |
| `extends`    | Добавляет возможности фиче, которая работает и без неё          | пунктирная       | «Расширяет» / «Расширяется функциональностью»          |
| `replaces`   | Пришла на смену другой (чаще всего архивной) фиче               | жирная           | «Заменяет» / «Заменена функциональностью»              |
| `related`    | Связь по смыслу без зависимости; симметрична                    | пунктир без стрелки | «Связана с»                                         |

Правила:

* **Блок `relations` и поле `depends_on` в нём обязательны** (так помечено в шаблоне). Если зависимостей нет, пишут
  `depends_on: []`; остальные типы связей (`extends`, `replaces`, `related`) указывают только при необходимости.
* **Ссылка на фичу — имя её файла без `.md`** (например, `auth-sms`); оно же стоит в якоре заголовка первого уровня.
  Поэтому при переносе спецификации в архив связи не ломаются. Имена файлов спецификаций должны быть уникальны.
* Элемент списка — имя файла либо набор `feature` + `note` (пояснение попадает в столбец «Комментарий» таблицы).
* **Каждую связь описывают один раз**, в спецификации-источнике («A зависит от B» пишут в A). Обратные связи
  («B используется в A») скрипт вычисляет сам и показывает в B. Дублировать их в B не нужно.
* Под названием фичи на схеме в квадратных скобках указан её статус; шрифт схемы равен шрифту таблиц темы
  (константа `MERMAID_FONT_SIZE` в скрипте). В таблице статус выводится только текстом, без значка.
* Стрелка на схеме идёт от субъекта связи к объекту: слева стоят фичи, которые зависят от текущей, расширяют или заменяют её,
  справа — то, от чего зависит или что расширяет и заменяет она сама. Текущая фича выделена толстой рамкой, архивные — пунктирной.
  По клику на узел схемы открывается спецификация; в таблице у названия есть окно предпросмотра, как в карте фичей.
* Если связей нет, раздел всё равно создаётся с пометкой «Связи с другими функциональностями в метаданных не заявлены».

Как это работает: скрипт `scripts/generate_docs.py` при каждом слиянии в `main` пересобирает раздел «Взаимосвязи»
во всех спецификациях между маркерами `<!-- relations:start … -->` и `<!-- relations:end -->` и коммитит файлы вместе
с картой фичей, если они изменились (повторный запуск без изменений метаданных ничего не меняет). Если маркеров в
спецификации ещё нет, раздел вставляется перед первым заголовком, который идёт за «Описанием». Вручную раздел не
редактируют, якорь `relations` в тексте спецификации не используют. В рабочих ветках скрипт запускать не нужно: достаточно
указать `relations` в метаданных. Изменение связи в одной спецификации обновит и разделы её соседей на `main`.

Что проверяет скрипт. Ошибка (сборка завершается с кодом 1): неизвестный тип связи или лишнее поле, ссылка на несуществующую
фичу, ссылка фичи на саму себя, два файла спецификаций с одинаковым именем, цикл в `depends_on`. Предупреждение: действующая
фича зависит от архивной или расширяет её, одна и та же связь указана дважды.

Адреса для кликов по узлам схемы рассчитаны на сайт с «чистыми» адресами (`.../auth-sms/`), которые Zensical использует
по умолчанию. Если в `zensical.toml` включены адреса вида `.html`, поменяйте `DIRECTORY_URLS` в скрипте.

### Раздел «Статистика»: плитки статусов и отбор на сайте

Раздел «Статистика» (карта, индексы разделов и модулей) начинается со свёрнутого инфо-блока «Статусы спецификаций»
(каждый статус в строке «значок название: пояснение», тексты из `STATUS_DESCRIPTIONS`), далее идут плитки статусов, строку отбора по названию и кнопку
«Сбросить». Сверху на всю ширину стоит плитка «Всего спецификаций» (общий итог, не кнопка, пересчитывается при отборе).
Ниже сетка плиток статусов: значок и число, под ними название статуса; плитки одной ширины и высоты и занимают всю ширину
страницы (на узкой странице сетка перестраивается в 3 или 2 колонки). Подсказок при наведении у плиток нет: статусы поясняет инфо-блок. Плитки работают как кнопки фильтра:
выбранные подсвечиваются, можно выбрать несколько (показываются фичи любого из статусов). Отбор по статусу и по названию
действуют одновременно: показывается то, что подходит под оба условия. Выбор сохраняется в адресе страницы
(`feature-map/?status=ready,development&q=заказ`), поэтому ссылкой можно поделиться. Если ничего не найдено, под полем
появляется сообщение «Нет данных, соответствующих условиям отбора»; сбросить отбор можно кнопкой «Сбросить» рядом с полем.

Правое меню («Содержание») на сформированных страницах скрыто: в их front matter стоит `hide: [toc]` (на
страницах-спецификациях оно остаётся). Колонка под него остаётся занятой (`extra.css`, раздел 11), поэтому ширина текста
такая же, как на странице «О программном продукте».

Списки спецификаций («Действующие спецификации», «Архив спецификаций», «Спецификации») — вложенные сворачиваемые блоки
«Модуль» → «Субмодуль»: в заголовке блока на первой строке название, на второй — итоги по статусам (значки и числа);
шрифт как у основного текста, цветной полосы за названием нет. Вначале всё свёрнуто; раскрыт может быть один модуль и
один субмодуль в нём. Пока действует отбор, это правило отключено, а блоки с совпадениями раскрыты автоматически; после
«Сбросить» всё снова свёрнуто.

Как это устроено: скрипт ставит на каждую ссылку атрибут `data-status`, на плитки — `data-filter`, блоки — `<details
class="feature-block">`. Клики, ввод и раскрытие блоков обрабатывает `theme-custom/javascripts/status-filter.js`
(подключён в `zensical.toml`), вид плиток и блоков задаёт `extra.css` (разделы 4, 5 и 10). Без JavaScript страница
показывает весь перечень (блоки раскрываются вручную).

### Меню сайта и индексы разделов

Меню формирует скрипт (блок `nav` в `zensical.toml` между маркерами `BEGIN/END GENERATED NAV`). Верхние вкладки —
«О программном продукте», «Карта функциональностей», «Глоссарий», «Спецификации» и «Архив спецификаций».

* При переходе на вкладку «Спецификации» или «Архив спецификаций» открывается индекс раздела
  (`docs/specifications/index.md`, `docs/archive/index.md`), а все группы (модули) в левом меню свёрнуты:
  вместо `navigation.sections` в `zensical.toml` включены `navigation.indexes` и `navigation.prune`, группа раскрывается
  только вместе с открытой в ней страницей.
* Индекс раздела построен как карта фичей: раздел «Статистика» (плитки статусов, строка отбора) и сворачиваемый перечень
  «модуль → субмодуль → фича», но **только по спецификациям своего раздела**: в индексе «Спецификации» — действующие,
  в индексе «Архив спецификаций» — архивные (в нём одна плитка «архив»). Индекс модуля устроен так же, но блоки только
  по субмодулям.
* Сгенерированные индексы помечены комментарием `<!-- generated: … -->` сразу после заголовка. По нему скрипт отличает
  свои файлы от созданных вручную, поэтому маркер не привязан к имени скрипта: скрипт можно переименовать
  без перегенерации индексов. Блок меню в `zensical.toml` ограничен маркерами `BEGIN/END GENERATED NAV`.
* Раздел определяется первой папкой пути спецификации (`specifications` или `archive`). Индексы разделов и модулей
  формирует скрипт, вручную их не правят; файл `index.md`, созданный вручную, скрипт не перезаписывает и предупреждает об этом.

### Значки статусов в левом меню

Перед названием каждой спецификации в левом меню стоит значок её статуса (тот же, что в карте функциональностей).
Его выводит сама тема по полю `icon` в метаданных спецификации (например, `icon: lucide/file-check`, набор lucide
встроен в Zensical). Поле `icon` вручную не заполняют: скрипт `scripts/generate_docs.py` ведёт его по полю `status`
(для файлов из `docs/archive/` — значок архива) и обновляет при каждой сборке вместе с картой и меню. Автор
указывает только `status`. Штатный значок темы «i» справа от названия и в правом оглавлении скрыт правилом
`.md-status` в `theme-custom/stylesheets/extra.css` (раздел 8).

Соответствие статусов и значков задано в `STATUS_ICONS` скрипта. Новый статус: добавьте его в `STATUS_ICONS` и в
`[project.extra.status]` файла `zensical.toml`.

### Итоги по статусам при отборе

Числа в разделе «Статистика» и счётчики в заголовках модулей пересчитываются при отборе по статусам и по названию
(`status-filter.js`) и всегда показывают то, что подходит под оба условия (выбранные статусы и текст). Числа на плитках
пересчитываются так же (у статусов, не попавших в отбор, будет 0).
Счётчики в заголовках модулей и субмодулей показывают то, что осталось в списке под заголовком; статусы с нулём там
скрываются. Без JavaScript и после «Сбросить» видны итоги без отбора. В разметке числа
стоят в `<span data-stat>` и `<span data-count-item>`: их формирует генератор.

### Порядок разделов и спецификаций в левом меню

По умолчанию модули и спецификации идут по алфавиту. Порядок меняют двумя простыми способами; менять `zensical.toml`
вручную не нужно (блок меню пересобирается скриптом).

* **Порядок спецификаций внутри модуля** — необязательное числовое поле `order` в метаданных спецификации. Меньше
  число — выше в меню. Нумеруйте с шагом 10 (10, 20, 30…): новую спецификацию можно вставить между двумя, не трогая
  остальные файлы. Спецификации без `order` идут после пронумерованных, по алфавиту.

  ```yaml
  feature_name: "Полнотекстовый поиск по названию"
  status: "released"
  order: 20
  ```

* **Порядок модулей** — список названий в файле `nav-order.yml` в корне репозитория (рядом с `zensical.toml`).
  Названия записывайте так же, как в поле `module`. Модули, которых нет в списке, добавляются в конец по алфавиту.

  ```yaml
  modules:
    - Каталог товаров
    - Управление заказами
    - Личный кабинет
  ```

Один и тот же порядок действует в разделах «Спецификации» и «Архив спецификаций», а также в карте функциональностей и
индексах разделов. При переносе файла в архив поле `order` сохраняется. Скрипт выдаст предупреждение, если в `order` не
целое число (сборка остановится), если модуль из `nav-order.yml` не найден (опечатка) или если у двух спецификаций одной
папки одинаковый `order`.

### Значки статусов в левом меню

Перед названием каждой спецификации в левом меню стоит значок её статуса (поле `status` в метаданных), тот же, что в
карте функциональностей. Значки заданы в `theme-custom/stylesheets/extra.css` (раздел 8). Чтобы добавить новый статус,
внесите его в `[project.extra.status]` в `zensical.toml` и в раздел 8 файла `extra.css`.

### Архив спецификаций

Чтобы архивировать спецификацию, переместите файл в `docs/archive/` с сохранением подпапки
(например, `docs/specifications/orders/order-cancel.md` → `docs/archive/specifications/orders/order-cancel.md`) — метаданные менять не нужно.
В карте фича перейдёт в раздел «Архивные функциональности» со значком 📦, ссылка останется рабочей.
Тот же результат даёт `status: "archived"` у файла вне папки архива.

### Локальный запуск

```bash
pip install -r scripts/requirements.txt
python scripts/generate_docs.py             # пересобрать карту, индексы, меню и разделы «Взаимосвязи»
python scripts/generate_docs.py --check     # проверить, что всё актуально (код возврата 1, если нет)
python scripts/generate_docs.py --validate  # только проверить спецификации (метаданные, связи, структуру), ничего не писать
python scripts/generate_docs.py --template другой-шаблон.md   # взять правила проверки из другого шаблона
```

Скрипт состоит из тонкой точки входа `scripts/generate_docs.py` и пакета `scripts/docgen/`. Работа идёт в четыре этапа:
чтение (`reader.py`) → проверка (`validate/`) → генерация (`generate/`) → запись или сверка (`apply.py`). Правила проверки
метаданных и заголовков берутся из шаблона (`template.py`). Ошибки в метаданных находит этап проверки до того, как что-либо
записано на диск. Подробнее о модулях — в `scripts/docgen/__init__.py`.

### Локальная проверка перед коммитом и push (pre-commit и pre-push)

Хуки лежат в `.githooks/` и запускают `python scripts/generate_docs.py --validate`: ту же проверку, что выполняется при
сборке сайта, но без записи файлов.

| Хук          | Когда срабатывает | Что делает                                                                           |
|--------------|-------------------|--------------------------------------------------------------------------------------|
| `pre-commit` | при `git commit`  | проверяет спецификации; при ошибке коммит отменяется, замечания выводятся с файлом и строкой |
| `pre-push`   | при `git push`    | повторяет проверку перед отправкой (на случай коммитов, сделанных в обход `pre-commit`)       |

**Включение (один раз в каждом клоне репозитория):**

```bash
pip install -r scripts/requirements.txt     # PyYAML для того же Python, который запускается командой `python`
git config core.hooksPath .githooks         # Git берёт хуки из папки проекта
```

Проверить: `git config core.hooksPath` должен вывести `.githooks`. Нужны Git, Python 3.10+ и PyYAML. В Linux и macOS файлам
хуков нужны права на исполнение (`chmod +x .githooks/*`); Git for Windows запускает хуки сам.

**Как это выглядит.** Испортите поле метаданных (например, сотрите `module`) и сделайте коммит: он будет отклонён, а в выводе
окажутся строки вида `ОШИБКА: docs/specifications/…/файл.md:12: …` и итог «Проверка не пройдена». Исправьте и повторите
коммит.

**VS Code.** Кнопка «Фиксировать» (Commit) запускает тот же хук. Текст ошибок виден в уведомлении и в «Вывод → Git». Задача
«Проверить спецификации» (`Ctrl+Shift+P` → «Tasks: Run Task», описана в `.vscode/tasks.json`) запускает проверку без коммита
и выводит замечания в панель «Проблемы» с переходом к файлу и строке.

**Обход.** На время разработки проверку можно пропустить: `git commit --no-verify` и `git push --no-verify`. Кнопка обхода в
интерфейсе VS Code включается настройкой `git.allowNoVerifyCommit`. Локальные хуки — это удобство, а не защита: они
настраиваются на каждом компьютере отдельно. Обязательной остаётся проверка при слиянии в `main`: тот же скрипт выполняет
все эти проверки, а ошибка в метаданных останавливает обновление карты и публикацию сайта.

**Если хук не срабатывает или падает:**

* `git config core.hooksPath` пуст: выполните команду включения из корня репозитория;
* `python: command not found` или открывается Microsoft Store: установите Python с python.org, отметив «Add python.exe to PATH»
  (хук сам выберет `python` или `python3`);
* `ModuleNotFoundError: No module named 'yaml'`: установите PyYAML в тот Python, который запускает хук
  (`python -m pip install pyyaml`);
* вместо кириллицы в выводе «кракозябры»: хуки уже выставляют UTF-8 (`PYTHONIOENCODING`, `LANG`, `LC_ALL`); при необходимости
  включите UTF-8 и в самом терминале.

### Настройки репозитория

**GitHub**

* Settings → Pages → Source: **GitHub Actions**.
* Settings → Actions → General → Workflow permissions: **Read and write permissions** (нужно для коммита карты).
* Если ветка `main` защищена правилом «только через Pull Request», разрешите обход правила для GitHub Actions
  либо замените `GITHUB_TOKEN` в шаге коммита на токен с правом записи.

**Gitea**

* Нужен зарегистрированный `act_runner` с меткой, указанной в `runs-on` файла `.gitea/workflows/pages.yaml`.
* Если ветка `main` защищена, разрешите пользователю, от имени которого workflow коммитит карту, прямую запись в `main`.

В обоих случаях `site_url`, `repo_url` и `repo_name` в разделе `[project]` файла `zensical.toml` укажите для своего сервера.
