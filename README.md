# example-app-requirements
Пример организации требований с использованием подхода "Documentation as Code"

Адрес сайта: https://dmitrykhilko.github.io/example-app-requirements/

## Как устроена карта фичей

Карта фичей (`docs/feature-map.md`) — иерархическое оглавление «Модуль → Субмодуль → Фича» со ссылками на
спецификации. **Вручную её не редактируют**: её формирует скрипт `scripts/generate_docs.py` по метаданным
(YAML Front Matter) в начале каждой спецификации.

```
Слияние в main ──► feature-map: python scripts/generate_docs.py ──► коммит docs/feature-map.md (если изменился)
                                                                        │
                                                                        ▼
                                                  deploy: zensical build ──► GitHub Pages
```

Workflow: `.github/workflows/deploy.yml`. Карта обновляется только при слиянии в `main`; в рабочих ветках
`docs/feature-map.md` не трогают, поэтому конфликтов слияния в нём не возникает.

### Метаданные спецификации

Шаблон — `templates/feature-spec-template.md`.

| Поле           | Обязательное | Описание                                                          |
|----------------|--------------|-------------------------------------------------------------------|
| `module`       | да           | Модуль (верхний уровень карты)                                    |
| `submodule`    | нет          | Субмодуль; по умолчанию `Общее`                                   |
| `feature_name` | да           | Название фичи — текст ссылки в карте                              |
| `status`       | рекомендуется| Статус фичи по жизненному циклу, см. таблицу ниже |

Каждая ссылка карты ведёт на раздел «Описание» спецификации и показывает его в окне предпросмотра при наведении
(`{data-preview}`).

**Якоря заголовков — обязательное условие.** У каждого заголовка спецификации должен быть явный якорь в конце строки,
как в `glossary.md`:

```markdown
# Отмена заказа клиентом {#order-cancel}
## Описание {#article-overview}
## Основной сценарий {#main-scenario}
## Критерии приёмки {#acceptance-criteria}
```

Идентификатор — латиница, цифры, `-`, `_`, первая буква; в пределах файла уникален. Заголовок «Описание» всегда
получает `{#article-overview}`. Нарушение любого правила — ошибка: сборка завершается с кодом 1 (в Actions — аннотация
с файлом и строкой), карта и сайт не обновляются.

Статьи без полей `module`, `submodule`, `feature_name` (например, глоссарий) в карту не попадают.
Если `module` или `feature_name` не заполнены, сборка тоже падает с указанием файла.
Неизвестный или пустой `status` приводит к предупреждению, фича показывается как `backlog`.

#### Статусы фичи

| Статус        | Значок                   | Что означает                                                                      |
|---------------|--------------------------|-----------------------------------------------------------------------------------|
| `backlog`     | `:lucide-file:`          | Зафиксированное сырое требование или идея                                         |
| `analysis`    | `:lucide-file-pen-line:` | Детализация и согласование требования                                             |
| `ready`       | `:lucide-file-check:`    | Утверждённое требование, готовое к реализации                                     |
| `development` | `:lucide-file-braces:`   | Требование в работе у команды разработки и тестирования                           |
| `released`    | `:lucide-file-text:`     | Код, связанный с требованием, успешно развёрнут на проде                          |
| `archived`    | `:lucide-file-archive:`  | Отклонённое или устаревшее требование; ставится автоматически для `docs/archive/` |

Допустимы русские синонимы: `бэклог`, `анализ`, `готово к разработке`, `разработка`, `реализовано`, `архив`.
Подписи статусов также заданы в `[project.extra.status]` файла `zensical.toml`; при изменении набора статусов
правьте оба места (`STATUS_ICONS`/`STATUS_TITLES` в скрипте и `zensical.toml`).

### Взаимосвязи фичей

Связи фичи с другими фичами задаются в метаданных блоком `relations`. На сайте в каждой спецификации сразу после
раздела «Описание» выводится раздел «Взаимосвязи» (`{#relations}`): **схема Mermaid и таблица только для этой
фичи и её прямых соседей**. Полная карта связей всего продукта не строится.

```yaml
relations:
  depends_on:                       # без этих фич данная не работает
    - feature: payment-sbp
      note: "Возврат средств выполняется тем же способом, которым оплачен заказ"
  extends: [filter-categories]      # добавляет возможности уже работающей фиче
  replaces: [search-old]            # заменяет (обычно архивную) фичу
  related: [auth-sms]               # просто связана
```

| Тип связи    | Когда использовать                                              | Стрелка на схеме | Строка в таблице (прямая / обратная)                  |
|--------------|-----------------------------------------------------------------|------------------|--------------------------------------------------------|
| `depends_on` | Без другой фичи эта не работает                                 | сплошная         | «Зависит от» / «Используется в»                        |
| `extends`    | Добавляет возможности фиче, которая работает и без неё          | пунктирная       | «Расширяет» / «Расширяется функциональностью»          |
| `replaces`   | Пришла на смену другой (чаще всего архивной) фиче               | жирная           | «Заменяет» / «Заменена функциональностью»              |
| `related`    | Связь по смыслу без зависимости; симметрична                    | пунктир без стрелки | «Связана с»                                         |

Правила:

* **Ссылка на фичу — имя её файла без `.md`** (например, `auth-sms`); оно же стоит в якоре заголовка первого уровня.
  Поэтому при переносе спецификации в архив связи не ломаются. Имена файлов спецификаций должны быть уникальны.
* Элемент списка — имя файла либо набор `feature` + `note` (пояснение попадает в столбец «Комментарий» таблицы).
* **Каждую связь описывают один раз**, в спецификации-источнике («A зависит от B» пишут в A). Обратные связи
  («B используется в A») скрипт вычисляет сам и показывает в B. Дублировать их в B не нужно.
* Под названием фичи на схеме в квадратных скобках указан её статус; шрифт схемы равен шрифту таблиц темы
  (константа `MERMAID_FONT_SIZE` в скрипте). В таблице статус выводится только текстом, без значка.
* Стрелка на схеме идёт от субъекта связи к объекту: слева стоят фичи, которые зависят от текущей, расширяют или заменяют её,
  справа — то, от чего зависит или что расширяет и заменяет она сама. Текущая фича выделена толстой рамкой, архивные — пунктирной.
  По клику на узел схемы открывается спецификация; в таблице у названия есть окно предпросмотра, как в карте фичей.
* Если связей нет, раздел всё равно создаётся с пометкой «Связи с другими функциональностями в метаданных не заявлены».

Как это работает: скрипт `scripts/generate_docs.py` при каждом слиянии в `main` пересобирает раздел «Взаимосвязи»
во всех спецификациях между маркерами `<!-- relations:start … -->` и `<!-- relations:end -->` и коммитит файлы вместе
с картой фичей, если они изменились (повторный запуск без изменений метаданных ничего не меняет). Если маркеров в
спецификации ещё нет, раздел вставляется перед первым заголовком, который идёт за «Описанием». Вручную раздел не
редактируют, якорь `relations` в тексте спецификации не используют. В рабочих ветках скрипт запускать не нужно: достаточно
указать `relations` в метаданных. Изменение связи в одной спецификации обновит и разделы её соседей на `main`.

Что проверяет скрипт. Ошибка (сборка завершается с кодом 1): неизвестный тип связи или лишнее поле, ссылка на несуществующую
фичу, ссылка фичи на саму себя, два файла спецификаций с одинаковым именем, цикл в `depends_on`. Предупреждение: действующая
фича зависит от архивной или расширяет её, одна и та же связь указана дважды.

Адреса для кликов по узлам схемы рассчитаны на сайт с «чистыми» адресами (`.../auth-sms/`), которые Zensical использует
по умолчанию. Если в `zensical.toml` включены адреса вида `.html`, поменяйте `DIRECTORY_URLS` в скрипте.

### Фильтр по статусам на сайте

Над перечнем функциональностей на странице карты расположены кнопки по статусам (значок и название) и кнопка «Сбросить».
Это ссылки с классом `.md-button`, их оформляет сама тема (документация Zensical, раздел «Buttons»). Выбранные кнопки
подсвечиваются; показываются только фичи выбранных статусов (если выбрано несколько — любого из них), пустые модули,
субмодули и разделы скрываются. Выбор сохраняется в адресе страницы (`feature-map/?status=ready,development`), поэтому
ссылкой можно поделиться.

Как это устроено: скрипт карты ставит на каждую ссылку атрибут `data-status`, а на кнопки — `data-filter`.
Клики обрабатывает `theme-custom/javascripts/status-filter.js` (подключён в `zensical.toml`). Счётчики в заголовках
модулей не меняются при фильтрации: это итоги по модулю. Без JavaScript страница показывает весь перечень.

### Меню сайта и индексы разделов

Меню формирует скрипт (блок `nav` в `zensical.toml` между маркерами `BEGIN/END GENERATED NAV`). Верхние вкладки —
«О программном продукте», «Карта функциональностей», «Глоссарий», «Спецификации» и «Архив спецификаций».

* При переходе на вкладку «Спецификации» или «Архив спецификаций» открывается индекс раздела
  (`docs/specifications/index.md`, `docs/archive/index.md`), а все группы (модули) в левом меню свёрнуты:
  вместо `navigation.sections` в `zensical.toml` включены `navigation.indexes` и `navigation.prune`, группа раскрывается
  только вместе с открытой в ней страницей.
* Индекс раздела построен как карта фичей: описание, статистика по статусам, отбор по статусу и названию и перечень
  «модуль → субмодуль → фича», но **только по спецификациям своего раздела**: в индексе «Спецификации» — действующие,
  в индексе «Архив спецификаций» — архивные (в нём только статус «архив» и поиск по названию).
* Сгенерированные индексы помечены комментарием `<!-- generated: … -->` сразу после заголовка. По нему скрипт отличает
  свои файлы от созданных вручную, поэтому маркер не привязан к имени скрипта: скрипт можно переименовать
  без перегенерации индексов. Блок меню в `zensical.toml` ограничен маркерами `BEGIN/END GENERATED NAV`.
* Раздел определяется первой папкой пути спецификации (`specifications` или `archive`). Индексы разделов и модулей
  формирует скрипт, вручную их не правят; файл `index.md`, созданный вручную, скрипт не перезаписывает и предупреждает об этом.

### Порядок разделов и спецификаций в левом меню

По умолчанию модули и спецификации идут по алфавиту. Порядок меняют двумя простыми способами; менять `zensical.toml`
вручную не нужно (блок меню пересобирается скриптом).

* **Порядок спецификаций внутри модуля** — необязательное числовое поле `order` в метаданных спецификации. Меньше
  число — выше в меню. Нумеруйте с шагом 10 (10, 20, 30…): новую спецификацию можно вставить между двумя, не трогая
  остальные файлы. Спецификации без `order` идут после пронумерованных, по алфавиту.

  ```yaml
  feature_name: "Полнотекстовый поиск по названию"
  status: "released"
  order: 20
  ```

* **Порядок модулей** — список названий в файле `nav-order.yml` в корне репозитория (рядом с `zensical.toml`).
  Названия записывайте так же, как в поле `module`. Модули, которых нет в списке, добавляются в конец по алфавиту.

  ```yaml
  modules:
    - Каталог товаров
    - Управление заказами
    - Личный кабинет
  ```

Один и тот же порядок действует в разделах «Спецификации» и «Архив спецификаций», а также в карте функциональностей и
индексах разделов. При переносе файла в архив поле `order` сохраняется. Скрипт выдаст предупреждение, если в `order` не
целое число (сборка остановится), если модуль из `nav-order.yml` не найден (опечатка) или если у двух спецификаций одной
папки одинаковый `order`.

### Архив спецификаций

Чтобы архивировать спецификацию, переместите файл в `docs/archive/` с сохранением подпапки
(например, `docs/specifications/orders/order-cancel.md` → `docs/archive/specifications/orders/order-cancel.md`) — метаданные менять не нужно.
В карте фича перейдёт в раздел «Архивные функциональности» со значком 📦, ссылка останется рабочей.
Тот же результат даёт `status: "archived"` у файла вне папки архива.

### Локальный запуск

```bash
pip install -r scripts/requirements.txt
python scripts/generate_docs.py          # пересобрать карту, индексы, меню и разделы «Взаимосвязи»
python scripts/generate_docs.py --check  # проверить, что всё актуально (код возврата 1, если нет)
```

### Настройки репозитория

* Settings → Pages → Source: **GitHub Actions**.
* Settings → Actions → General → Workflow permissions: **Read and write permissions** (нужно для коммита карты).
* Если ветка `main` защищена правилом «только через Pull Request», разрешите обход правила для GitHub Actions
  либо замените `GITHUB_TOKEN` в шаге коммита на токен с правом записи.
